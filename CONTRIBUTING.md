# Contributing to PDFree

## Architecture

PDFree is a fully client-side PDF tool suite. All processing happens in the browser via Web Workers — nothing is uploaded to any server. See [README.md](README.md) for the project pitch and [CLAUDE.md](CLAUDE.md) for the full build/deploy workflow and homepage-editing checklists.

### Module map

```
scripts/build.py         ← Static-site generator: Jinja2 templates + data/ → dist/ (364 pages,
                            14 locales). index.html + 13 locale homepages are hand-authored, not
                            generated — they embed the same #toolArea inline for client-side
                            tool switching without a page load.
scripts/templates/
  tool-page.html          ← Shared Jinja template for every generated per-tool, per-locale page
data/tools-config.json    ← Tool metadata + UI strings, all 14 locales
data/content/<lang>/      ← SEO body copy per tool per language

js/
  app.js                  ← Entry point: routing, hero drop zone, search, event wiring
  config.js                ← TOOLS dict: icon, titles/descs per locale, accept, implemented
  toolRegistry.js          ← Single source of truth for tool wiring — see below
  toolRegistrations.js     ← Every *UI module's registerTool() call lives here
  processor.js              ← runnerMap dispatches to worker.js or a main-thread runner
  worker.js                 ← Heavy PDF operations (pdf-lib, OffscreenCanvas) — OFF-LIMITS, see CLAUDE.md
  ui.js                      ← Toast, progress bar, section show/hide
  files.js                   ← File drop/select, validation, drag-to-reorder
  analytics.js                ← Privacy-first event tracking → /api/analytics → Cloudflare Workers
                                 Analytics Engine (see src/index.js). Not Plausible — that was an
                                 earlier, since-replaced integration.
  <name>UI.js                 ← Per-tool options panel (compressUI, mergeUI-equivalent, etc.)
sw.js                          ← Service worker (auto-generated by build.py — do not hand-edit)
manifest.json                  ← PWA manifest
src/index.js                    ← Cloudflare Worker: routing, redirects, /api/analytics relay
```

### Adding a new tool

As of the tool-registry refactor, this is a 3-step process — `toolRegistry.js`'s own header
comment states it exactly:

1. Add a `TOOLS` entry in `js/config.js`.
2. Create a `js/<name>UI.js` module and call `registerTool(key, { init, hide, getParams, runner, ... })`
   in `js/toolRegistrations.js` — see that file's descriptor-shape comment in `toolRegistry.js` for
   the full set of optional fields (`validate`, `presetFilter`, `multiFile`, `minFiles`, etc.).
3. If the tool needs a new kind of processing (not reusable via an existing `runner`), add a
   `case` in `worker.js` and a `runnerMap` entry in `processor.js`.

That's it for the JS side — `app.js`/`processor.js` never need per-tool edits, by design.

**The part that's easy to miss**: every tool also needs a `<div id="<name>Options">` container
wherever its UI module looks it up — not just on the dedicated SSG-generated tool page, but on
**all 14 real homepages**, since they embed `#toolArea` inline too. `scripts/check_dom.py` fails
the build if any homepage is missing one, and `build.py` self-heals it into `dist/` as a last-resort
safety net — but fix the source homepage file for real if you see that warning. Full checklist,
including the separate one for tools whose primary input is a new raw file type (not PDF/image), is
in [CLAUDE.md](CLAUDE.md) — this has been a real, repeated source of "works everywhere except one
homepage" bugs, worth reading before adding a tool.

### Testing

43 test files, 930 assertions (`npm test`), covering pure logic (`utils.js`, per-tool param
builders), `worker.js` handlers via real PDF fixtures in `tests/fixtures/`, and a few real-browser
Playwright E2E specs (`tests/e2e/`) for regressions that need an actual rendered page to catch.
`npm run validate` runs the full gate: DOM/i18n checks, lint, tests, build.

### Known constraints

- **CDN dependency**: `pdf-lib`, `JSZip`, `docx`, `exceljs`, `pptxgenjs`, and `pdf.js` load lazily
  from CDN on first use (`js/lazyLibs.js`), not bundled locally. The service worker caches them
  after first use, but a tool's first-ever use on a given device requires internet. No plan to
  bundle these locally — the lazy-load-on-demand pattern is deliberate (keeps initial page weight
  down; see the eager-loading regression fixed in commit `3796fb6` for why this matters).
- **Off-limits files** (see [CLAUDE.md](CLAUDE.md) for the full, current list and why): `js/vendor/`,
  `js/worker.js`, `sw.js`.
