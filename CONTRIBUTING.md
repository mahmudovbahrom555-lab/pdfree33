# Contributing to PDFree

Thanks for considering a contribution. PDFree focuses on privacy-first, browser-based PDF tools. Start with a reproducible bug, a small improvement, or a documentation fix; discuss substantial changes in an issue before implementing them.

**Do not attach confidential or user-supplied PDFs to public issues or pull requests.** Use synthetic or redistributable test files. For vulnerabilities, follow [SECURITY.md](SECURITY.md) rather than opening a public bug report.

## Requirements

- Node.js 20 is used in the deployment workflow (`.github/workflows/deploy.yml`).
- Python 3 (CI uses Python 3.12) and `jinja2` for the static-site build.
- A modern browser. Chromium/Playwright is needed only for optional browser E2E tests.
- Internet access may be needed for initial npm installation and first-time browser library loading.

## Quick start

```bash
git clone https://github.com/mahmudovbahrom555-lab/pdfree33.git
cd pdfree33
npm ci
python3 -m pip install jinja2
python3 scripts/build.py
python3 -m http.server 8080 --directory dist
```

Visit `http://localhost:8080/`. The build creates `dist/`; do not hand-edit generated output. For a containerized deployment, see [SELF_HOSTING.md](SELF_HOSTING.md).

## Checks before a PR

```bash
npm test               # Node and Python tests from package.json
npm run lint           # ESLint
npm run validate       # DOM/i18n/vendor checks, lint, tests, build
npm run check:claims   # separate copy/claim checker
```

`npm run validate` runs the checks listed in the current `package.json`; it does **not** include every E2E or production smoke test. When modifying user-visible behavior, run the relevant browser test as well. For example, with `dist/` served locally in a separate terminal:

```bash
npx playwright install chromium
PDFREE_BASE_URL=http://localhost:8080 npm run test:e2e:compress
```

Other `test:e2e:*` scripts are listed in `package.json`. Some quality/corpus tests have additional prerequisites; consult the relevant test or workflow before running them. Do not use real user documents as fixtures.

## Architecture at a glance

| Path | Purpose |
| --- | --- |
| `scripts/build.py`, `scripts/templates/`, `data/` | Generate localized tool pages and static assets |
| `js/app.js`, `js/config.js` | App entry point and tool definitions |
| `js/toolRegistry.js`, `js/toolRegistrations.js` | Tool lifecycle registration and routing |
| `js/processor.js`, `js/worker.js` | Processing dispatch and PDF work |
| `js/*UI.js` | Individual tool controls |
| `js/fileLimits.js` | Tool-specific file-size limits |
| `js/lazyLibs.js` | On-demand library loading |
| `js/analytics.js`, `src/index.js` | Usage events and site Worker endpoints |
| `tests/`, `tests/e2e/` | Automated and browser tests |

For details on the registry descriptor, read the header of [`js/toolRegistry.js`](js/toolRegistry.js). The build's `HOMEPAGE_LANGS` in [`scripts/build.py`](scripts/build.py) is the source of truth for which localized homepages contain the interactive tool area; avoid hard-coded locale counts in documentation.

## Making changes

1. Search existing issues; explain the user problem and how to reproduce it.
2. Keep changes focused. Include a regression test when fixing behavior.
3. If adding a tool, update its definition and registration, and verify its options container on every applicable homepage, not only the dedicated tool page. See `js/toolRegistry.js` and `scripts/check_dom.py`.
4. Treat `js/worker.js`, `js/vendor/`, and the generated `sw.js` as protected/high-risk areas. Do not modify them without maintainer agreement; `sw.js` is generated by the build.
5. Run relevant checks, describe what you actually tested, and note limitations in the PR.

PDFree processes PDF content locally for its browser tools, but the site also sends coarse analytics events and optional user-submitted feedback. Avoid claims such as “no network requests,” “unlimited file size,” or “all features always work offline.” Review [README.md](README.md) and `js/fileLimits.js` when documenting behavior.
