# CMYK/grey JPEG prototype — PRE-REGISTERED 2026-11-06 (owner approved the prototype; NOT integration)

Order fixed by the owner: **decoder → encoder → independent checks**. Nothing goes into js/ or the
site from this stage. Encoder choice (own vs libjpeg-turbo WASM) is NOT made yet.

## Stage 1 — decoder (this file's first part)
**Decoders under test:**
- pdf.js JpegImage 4.10.38 (image_decoders build, the version the site vendors) — independent code;
- libjpeg-turbo 3.2.0 (C, our own small tool `ljtool`), fancy upsampling on and off;
- MuPDF (fitz) and Ghostscript renders of a PDF holding the JPEG — both libjpeg (IJG) lineage,
  so NOT fully independent of libjpeg-turbo; reported as such. Pillow bundles libjpeg-turbo too.

**Q1 Headers** (all DCT images of the 17 DEV docs): components, APP14 present/transform, sampling
factors, progressive/baseline, ICC (APP2), /Decode, /ColorSpace in the PDF. Counts per kind.

**Q2 The 43–77 difference** (pdf.js vs libjpeg on real files). Hypothesis (labelled): chroma
upsampling (pdf.js nearest, libjpeg "fancy"). Confirmed only if libjpeg with fancy upsampling OFF
matches pdf.js within max |Δ| <= 2 on the same files; otherwise the cause stays open and is
looked for in raw channels / inversion / YCCK math before any encoder work.

**Q3 Control images with known values** (generated by ljtool, never user documents):
- patches 0/25/50/75/100 % of each of C, M, Y, K; rich black (C60 M40 Y40 K100); pure-K text
  strokes 1–4 px; a K ramp; a grey 1-channel ramp; a two-ink stamp-like red (M100 Y100) disc;
- encoded as CMYK (APP14 transform 0), YCCK (transform 2), grey; sampling 1×1 and 2×2; q100 and q75.
- **Pass for a decoder (q100, 1×1):** patch centre means within ±2/255 of the known value for every
  ink, the Adobe inversion read right (100 % C reads as full cyan, not as no ink). A decoder failing
  this for a mode is not used for that mode.
- At 2×2 / q75 the decoders are compared to each other and to the known values; reported, no pass/fail.

wrong "fix" was made and reverted the same hour, and no run used it.

**Q3 controls (pass = q100 4:4:4 patch centres within ±2):**

- **pdf.js decoder PASSES Q3.**

**Q2 the 43–77 difference** (pdf.js vs libjpeg-turbo, real files):
- with fancy upsampling OFF: plain CMYK max 1, YCCK max 3 (0.001–0.003 % of samples > 2), grey max 1;
- with it ON: max 43–77, 0.9–5.6 % > 2;

## Stage 2 — encoder via the chain "own worker + the site's qpdf WASM" (owner APPROVED 2026-11-06, PRE-REGISTERED before any run)
Encoder alternatives (new library, own encoder) are deferred until this fails.

**What encodes:** qpdf 12.2.0 WASM (js/vendor/qpdf/lib, the site's copy) run as
`--optimize-images --oi-min-width=0 --oi-min-height=0 --oi-min-area=0 --jpeg-quality=75` on a
one-image temp PDF whose image is stored UNCOMPRESSED (so DCT is always smaller). In qpdf's source
this is QPDFJob ImageOptimizer → Pl_DCT (libjpeg, jpeg_set_defaults, in_color_space JCS_CMYK /
JCS_GRAYSCALE). No wrapper of ours in between. The JPEG bytes are taken from qpdf's output.
**What decodes / resamples (JS, as the browser would):** pdf.js JpegImage 4.10.38 for DCT inputs
(CMYK, YCCK, grey); raw bytes for Flate inputs; downsampling = area average (box filter; chosen
before the run: no ringing, so no ink appears where there was none — the Python prototype's
Lanczos differs, reported).
**Scope (fail-closed):**
- in: DeviceCMYK or DeviceGray, 8-bit, single DCT or Flate filter (Flate: no /DecodeParms predictor);
- /Decode absent or the full inverse;
- SMask kept byte for byte;
- skipped and counted: /Mask, ICCBased, Indexed, DeviceN, Separation, Lab, non-Adobe 4-channel JPEG,
  progressive JPEG, anything a step fails on.
- The image is replaced only if smaller. Effective dpi from the largest placement, resample only if > 220
  (target 200).

**A. decode + downsample** (controls): output size = round(w·s) × round(h·s); channels 4 / 1;
flat-patch centres unchanged within ±1 after downsampling.
**B. qpdf JPEG** (controls, q75):
- SOF components 4 with APP14 transform 0 (CMYK), or 1 (grey);
- patch centres within ±3 of the known inks;
- pure-K patches and their interiors: C, M, Y <= 2.
**C. in the PDF:** the same controls embedded; read by 4 decoders — libjpeg-turbo (ljtool, raw), pdf.js
decoder, MuPDF render, Ghostscript render; each within ±3 on patch centres; no inversion.
**D. 17 DEV docs** vs PDFree today (L):
- size reported per doc and in total, next to the Python D200q75;
- worst-page ink |Δ| vs L (50 dpi, 4 pages, the compare.py method) and d_metrics V1/V5/ΔE;
- **blocking:** any doc whose worst-page |Δ| vs L exceeds the Python D200q75's by more than 0.1 →
  stop and explain before going on.
- Also recorded: per-image pure-K guard rejects (the guard compares source vs re-decoded
  output with the SAME decoder, pdf.js).

**Not in this stage:** K-only CMYK → grey, Flate around DCT, font dedup — measured separately later.
**No js/ change, no site change, no PR to main.**

## Stage 3b — fine-detail study (PRE-REGISTERED 2026-11-06, before any 3b measurement)
**Population:** the images Stage 2's chain DOWNSAMPLED in the 17 docs (effective dpi > 220). Images
only re-encoded at their own size are out of this question.

**Ground truth by eye:** every downsampled image (or, if over 300, a random sample of 300, seed
20261106) is labelled from a thumbnail plus a 1:1 crop of its busiest region:
- PHOTO (continuous tone);
- DETAIL (text, line art, diagrams, maps, scanned pages with text, screenshots with text);
- MIXED (a photo with text in it);
- UNSURE.
Labelled by me, before any classifier is run on them; the label file is committed first. The
owner may re-label; his labels win.

**Classifier v0 (written before looking at its results on the labels):** features per image at
source size:
- share of near-flat 8×8 blocks;
- share of strong edges (|∇| > 64);
- number of distinct quantised colours (16 levels per ink).

DETAIL if flat share ≥ 0.5 and edge share ≥ 0.02, or colours ≤ 64; PHOTO otherwise. Thresholds
fixed now; v0 is judged, not tuned. A tuned v1 would be a new version judged on a held-out half.

**Reported:**
- (1) count and MB by label;
- (2) the MB D saves on DETAIL+MIXED+UNSURE at 200 dpi, and what it would save at 300 dpi and
  with no downsampling (re-encode only) — i.e. the MB lost by protecting them;
- (3) quality per label at 200/300/none: G3 is not available on real images (no element boxes),
  so the 99.5th-percentile ink of the busiest region, kept %, plus crops;
- (4) classifier v0 confusion vs the labels. Misses (a DETAIL called PHOTO) are counted
  separately and listed — small text in scans called PHOTO is the failure that matters.

**Nothing is decided from 3b alone:** a new criteria version is written from it, for the owner.
